# Week 1 复盘：Harness Engineer 方法论笔记

> 一周成果：把 Harness 五方面能力（D1-D5）逐一落地到 ai-agent-cli（80+ 离线测试全绿），
> D6 集中装配，D7 沉淀为可复用模板。
> 本篇是"方法论"而非"代码清单"——每方面回答三个问题：

## 1. 上下文工程（D1）

**为什么这样设计**：LLM 无状态，"记忆 = messages"；但 messages 无限累积会让 token
成本线性爆炸。解法是三层记忆——长期（TaskMemory 固定预算 1500 字符，只 merge 增量去重）、
中期（增量摘要槽，旧摘要作高优先级输入防稀释）、短期（滑动窗口 N 轮有界）；
外加审计（每层多大、还剩多少窗口）与检索注入（大文档不常驻，提问时按关键词找回）。

**不设计会怎样**：100 轮会话原文常驻 ~5 万字符且线性涨，500 轮就爆 128k 窗口；
模型"忘记"用户第 1 条消息里的关键约束（因为被挤出窗口）。

**换方案会牺牲什么**：
- 只做滑动窗口（不做任务记忆）：实现最简单，但**早期关键约束会丢**——用户第一条
  "目标"是最重要的信息，不该和中间过程消息同等待遇
- 只做全文摘要（不做分层）：摘要会随压缩链逐级稀释，第 5 次压缩后早期细节基本没了
- 纯向量库 RAG（不做 TaskMemory）：召回是概率性的，任务级约束（"必须用 Python"）
  可能召不回——**规则性信息适合确定性提取，知识性信息才适合向量检索**

## 2. 约束设计（D2）

**为什么这样设计**：Agent 的"行动力"必须配上"边界"。三件套——工具 risk 分级
（safe 直通 / confirm 审批）、LLM 重试（只重试"对方暂时不可用"的错）、降级策略清单
（六类失败场景预写"触发条件 + 动作 + 用户可见信息"）。审批被拒返回 `[用户拒绝]`
字符串回喂——**拒绝本身也是模型可读的信息**，模型会换方案而不是崩溃。

**不设计会怎样**：`run_shell("rm -rf .")` 静默执行；网络抖动一次任务全废；
"出问题怎么办"全靠临场反应，行为不可预期。

**换方案会牺牲什么**：
- 权限白名单硬编码（只允许 N 条命令）：最安全，但**堵死了工具的全部灵活用法**，
  模型无法组合命令完成任务——约束的粒度应该"每次操作"而非"每类操作"
- 不重试直接失败：最省事，但限流/抖动在真实 API 上是常态，一次失败率可能高 10 倍
- 审批全人工（每步都问）：token 省了，但交互成本爆炸——所以只对 confirm 级工具问，
  只读工具零打扰

## 3. 工具编排（D3）

**为什么这样设计**：三个层次——接入（MCP 自动注册外部工具）、顺序（depends_on
依赖声明，"写之前必须读过"）、委派（delegate_task 子 Agent，独立上下文只回结论）。
MCP 用 asyncio.run 桥接同步循环（SDK 纯 async）；委派做了三个安全设计：
过滤委派工具防递归、调用历史备份恢复、审批继承防绕过。

**不设计会怎样**：外部能力接不进来（每个 server 手写适配）；模型乱序操作
（没读就写，覆盖了不该覆盖的）；长任务把主上下文塞爆（子任务的中间过程全在主线程里）。

**换方案会牺牲什么**：
- MCP 不做（每个工具手写）：依赖成百上千的 SDK 特判，N 个 server = N 份胶水代码
- 依赖用 Prompt 软约束（只在提示词里说"先读再写"）：零代码，但模型"偶尔"不遵守——
  **关键不变量应靠机制（代码检查）而非提示（概率遵守）**
- 子任务也在主上下文做：实现最直，但多轮工具调用的中间消息全部污染主 Agent 记忆

## 4. 规格治理（D4）

**为什么这样设计**：constitution（宪法，5 条不可违反）→ spec（工具契约表）→
plan（路线）→ tasks（任务模板）四级体系写进 AGENTS.md；版本号 + 变更日志 + git tag；
`scripts/check_spec.py` 用 ast 双向对比"代码注册 vs spec 表格"，脱节退出码 1。
**规格与代码的一致性靠工具保证，不靠人自觉**。

**不设计会怎样**：Agent 每次开工都"读文档才知道规矩"且文档很快过期；工具加了
spec 没更新 → 另一个 AI 照旧 spec 实现，产出的代码对不上。

**换方案会牺牲什么**：
- 只有 constitution（不要 spec 层）：原则有余细节不足——"不猜测"无法约束
  "write_file 的参数是什么"
- 规格放代码注释（不要独立文档）：代码里能搜到，但**跨文件/跨会话的一致性视图**没了，
  而且外部 AI（不经代码）无法遵循
- 一致性靠 code review（不要脚本）：人的注意力有限，check_spec 这种可自动化的
  检查不该占人的时间——机器能查的交给机器

## 5. 质量闭环（D5）

**为什么这样设计**：验证不只在最后测一次，而是**嵌进 Agent 循环的每一步**——
工具执行成功后自动触发验证点钩子（write_file 后跑 pytest），失败输出作为 tool
消息回喂 → 模型修复 → 再验证，循环至绿。契约校验在注册时就检查 schema 与 handler
签名一致（把运行时错误提前到装配时）。

**不设计会怎样**：Agent"写完代码就声称完成"——没跑过测试的代码等于没验证；
schema 与 handler 不一致的错误直到模型实际调用才炸，浪费一轮轮调试。

**换方案会牺牲什么**：
- 只在最后跑一次测试（验证后置）：简单，但**失败定位要回溯整段对话**——
  每步验证把"哪一步引入的 bug"定位在毫秒内
- 验证失败就硬停（不给模型修复机会）：最严格，但模型本来能修，硬停把
  "机器能完成的修复"推给人
- 不做契约校验（运行时才暴露）：少一段代码，但"注册 100 个工具后哪个 schema 错了"
  的排查成本远超校验那几行

## 6. 贯穿全程的三条元原则

1. **关键不变量靠机制，不靠提示**：tool_call_id 配对、handler 返回 str、危险操作审批
   ——全在代码里强制，Prompt 只表达"偏好"不承载"必须"
2. **失败是可恢复的对话事件，不是崩溃**：工具错误、审批拒绝、验证失败——全部转成
   字符串回喂模型，模型拥有"感知 → 决策 → 行动"的闭环（docs/fallback-policy.md）
3. **单向依赖 + 集中装配**：入口 → 编排 → 基础设施分层；所有开关收敛到 config.py
   ——新增能力永远只动一处

## 7. 如果重新来一遍

- 更早做 config.py（D1 就引入），避免中间各天把开关散在 agent_cli.py
- 审计（D1）应从一开始就在——它让你看到"三层记忆"每个决策的真实代价
- 测试先行：每个能力当天就补 ScriptLLM/Fake 用例，攒到最后再补会失去回归价值
